# 工程化流程安装包

> 用法:把本文件拖进另一台电脑的 Cursor 对话框,说「按这个文件安装」。agent 会按下面的指令把整套流程装到全局。
> 本文件由 `del/build-flow-bundle.mjs` 从已安装的 skill 生成,改完 skill 后重新运行即可更新。

## 给 agent 的安装指令

1. 目标目录:用户主目录下的 `.agents/skills/`(Windows 为 `%USERPROFILE%\.agents\skills`),不存在则创建。
2. 对下面「文件清单」逐项处理,路径相对目标目录,内容**原样**写入,不要改动、不要总结:
   - 写 `grilling/SKILL.md` 之前,若该文件已存在且 `grilling/SKILL.md.orig` 不存在,先把现有 `SKILL.md` 复制为 `SKILL.md.orig`(保留那台电脑上的原版)。
   - 其他文件直接覆盖。
3. 不要修改任何项目文件。
4. 装完后验证 5 个文件都存在,然后告诉用户:
   - 需要**手动**把下面「用户规则文本」粘贴到 Cursor 设置 → Rules → User Rules(这是应用设置,不是文件,你改不了)。
   - 在新窗口怎么开始,见「怎么用」。
5. 若当前项目的 `.cursor/rules/00-meta.mdc` 里有「grilling 提问方式」小节,提示用户:该内容已并入全局 grilling,可以删掉;删改前需用户确认。

## 流程

```
grilling(agent 提议 小/中/大,你拍板)
  → docs/specs/<功能>/共识.md(固定模板)     ← 这里停下,不开干
  → [你确认]
  → 大功能:/spec(spec.md 勾选清单 + tickets/)→ [你确认]
  → /implement(大功能:/implement NN,每条新开 session;中等:直接做)
  → /review(对照 spec + 项目规则;中大任务多一遍 ponytail-review,只出建议)
  → 经验总结(仅有信号:偏离 spec → 复盘.md;规则级的坑 → 走项目 #rule 流程)
  → 功能收官:/ponytail-debt
```

- 小任务(改 bug、微调、单文件)直接做,不走流程。
- 状态只记在 `spec.md` 的勾选清单里。
- 项目要用别的目录或模板时,在项目规则里写一条覆盖说明即可。

## 用户规则文本(手动粘贴到 Cursor 设置 → Rules → User Rules)

工作流:遇到非小任务(新功能、需求不明确、涉及多个模块)时,先使用 grilling skill:提议 小/中/大 路径并等我确认;grilling 达成共识后只写 docs/specs/<功能>/共识.md 然后停下,我明确说"开干/实现"之前不得改代码。小任务(改 bug、微调、单文件)直接做。大功能用 /spec 拆 ticket、/implement NN 逐条实现(每条新开 session)、/review 审查;中等任务共识后直接 /implement。

## 怎么用

- 新窗口直接描述想做的事(「我想做个 XX 功能」),上面的用户规则会让 agent 先走 grilling。想强制走流程时,开头写 `/grilling`。
- 共识文档写完后:大功能说 `/spec`;确认 ticket 后在**新窗口**说 `/implement 01`;中等任务直接说 `/implement`。
- 随时可单独说 `/review` 审查当前改动。

## 文件清单

### `grilling/SKILL.md`

````markdown
---
name: grilling
description: Grill the user relentlessly about a plan or design, then write a consensus doc and stop before coding. Use when the user wants to stress-test a plan before building, uses any 'grill' trigger phrases, or starts a non-trivial task (new feature, unclear requirements, change spanning several modules, design before implementation).
---

Interview me relentlessly about every aspect of this plan until we reach a shared understanding. Walk down each branch of the design tree, resolving dependencies between decisions one-by-one. For each question, provide your recommended answer.

Ask the questions one at a time, waiting for feedback on each question before continuing. Asking multiple questions at once is bewildering.

If a *fact* can be found by exploring the codebase, look it up rather than asking me. The *decisions*, though, are mine — put each one to me and wait for my answer.

Do not enact the plan until I confirm we have reached a shared understanding.

## How to ask

Ask in plain text in your reply, with your recommended answer, and let me answer in the input box. Never use the AskQuestion multiple-choice tool during grilling.

## Before the first question: propose a track

Judge the task size and propose a track in one or two sentences; I decide. Do not pick it silently.

- **Small** (bug fix, tweak, single file): skip grilling, just do it.
- **Medium** (one feature, a few decisions): grilling → `共识.md` → [my confirm] → `/implement` → `/review`.
- **Large** (spans several modules): grilling → `共识.md` → [my confirm] → `/spec` (ticket list) → [my confirm] → `/implement NN` per ticket, each in a new session → `/review`.

## When we reach shared understanding: write the doc, then stop

Writing the consensus doc is the ONLY action allowed at this point. Do not edit code.

1. Write `docs/specs/<feature>/共识.md` (create dirs as needed; if the project's rules define another location, follow them) using this template:

        # <feature> 共识
        ## 目标
        One or two sentences.
        ## 已定决策
        Every decision I made during grilling, each with its reason.
        ## 不做什么
        Explicitly excluded scope.
        ## 验收标准
        How we know it is done. Checkable items.
        ## 涉及范围
        Expected directories / files.

2. Tell me the file path, then ask which step is next (per the agreed track). If the project's rules ask for something at the end of grilling (e.g. capturing rules), ask that in the same message.
3. Wait for my explicit go-ahead ("开干", "实现", "/spec", "/implement" …). Without it, do not modify any code.
````

### `spec/SKILL.md`

````markdown
---
name: spec
description: Turn an approved consensus doc (共识.md) into spec.md with a technical design and a checkbox ticket list, plus one file per ticket. Use for LARGE tasks after grilling, when the user says /spec or asks to split a design into tasks. Does not write code.
disable-model-invocation: true
---

Turn `共识.md` into an implementable spec and independent tickets. Do not write or modify any code.

## Input

`docs/specs/<feature>/共识.md` (the user may pass the feature name; otherwise use the most recently modified one). If the project's rules define another location, follow them. If the file does not exist or has empty 验收标准 / 不做什么, stop and send the user back to `/grilling`.

## Steps

1. Read `共识.md`, then explore the codebase and the project's rules (`.cursor/rules`, `AGENTS.md`, …) for the facts the design depends on. Do not ask the user things the code can answer.
2. Write `spec.md` next to it:

        # <feature> Spec
        来源:共识.md
        ## 技术设计
        Approach, key structures/APIs, how it fits existing modules, risks.
        ## Tickets
        - [ ] 01 <name> — one line
        - [ ] 02 <name> — one line (依赖 01)

3. Write `tickets/NN-<name>.md` for each ticket:

        # NN <name>
        ## 目标
        ## 范围(文件/目录)
        ## 验收标准
        Checkable items, taken from or refined from 共识.md.
        ## 依赖
        Which tickets must be done first, or "无".
        ## 不做
        Out-of-scope items that a ticket reader might be tempted to do.

## Ticket rules

- Each ticket must be completable in one session, by someone who reads only `spec.md` and that ticket.
- Each ticket leaves the project in a working state; order tickets so dependencies come first.
- Status lives ONLY in the `spec.md` checkbox list. Ticket files carry no status.
- Every 验收标准 item in 共识.md must be covered by at least one ticket.

## Finish

Show the ticket list, then stop and wait for my confirm. Tell me to run `/implement 01` in a NEW session.
````

### `implement/SKILL.md`

````markdown
---
name: implement
description: Implement one ticket (large task) or the whole consensus doc (medium task) exactly as documented, then run /review. Use when the user says /implement, /implement 01, or asks to start coding after grilling/spec is confirmed.
disable-model-invocation: true
---

Implement what the documents say, nothing more. Argument: ticket number (e.g. `01`) for large tasks; none for medium tasks.

## Locate the docs

`docs/specs/<feature>/` (or the location set by project rules). If several features exist, use the most recently modified or ask.

- **Large task** (`spec.md` exists): read `spec.md` and ONLY the requested `tickets/NN-*.md`. Do not read other tickets.
- **Medium task** (only `共识.md`): read `共识.md`; its 验收标准 is the done-criteria.
- Neither exists: stop, tell the user to run `/grilling` first. Never start from chat memory alone.

## Session check (large tasks)

If this conversation already contains the grilling or spec discussion, or is long, tell the user to run `/implement NN` in a NEW session and stop. Medium tasks may continue in the current session.

## Steps

1. Large: verify every ticket in 依赖 is checked in `spec.md`; if not, stop and say which.
2. Read the project's rules that apply to the files you will touch (`.cursor/rules`, `AGENTS.md`, …) before editing.
3. Implement strictly within 范围 and 验收标准. Respect 不做 / 不做什么.
4. If something outside scope is needed, or the doc is ambiguous or contradicts the code: stop and ask. Do not silently widen scope or change the design. Small unrelated findings: list them at the end, do not fix them.
5. Run the project's lint / type check / tests where they exist; fix what you broke.
6. Run `/review` on your changes. Fix every Critical finding, then re-review once.
7. Large: tick this ticket in `spec.md` (`- [x] NN …`). Only the checkbox changes.

## Finish

Report: what was done, acceptance items met, findings left unfixed, and the next ticket (large) or "done" (medium). When the last ticket is ticked, suggest `/ponytail-debt` once.
````

### `review/SKILL.md`

````markdown
---
name: review
description: Review code changes against the consensus doc / ticket acceptance criteria and the project's rules, add an over-engineering pass for medium/large tasks, and capture lessons only when there is a signal. Use when the user says /review, asks to check the work, or after /implement (it calls this automatically).
disable-model-invocation: true
---

Review the current changes (`git diff`, staged + unstaged, plus untracked files). Report only; do not modify code unless the caller (`/implement`) asks you to fix Critical items.

## 1. Spec compliance

Read `docs/specs/<feature>/共识.md` (and the ticket if reviewing one). Check:
- Every 验收标准 item in scope is met.
- Nothing from 不做什么 / 不做 was done.
- No changes outside 范围.
- Decisions in 已定决策 are respected.

No docs (small task): skip this section.

## 2. Project rules and correctness

Read the project's rules that apply to the changed files (`.cursor/rules`, `AGENTS.md`, …) and check compliance. Then check correctness, error handling, and obvious bugs in the diff. Run lint / type check when available.

## 3. Over-engineering pass (medium and large tasks only)

If the `ponytail-review` skill is available, apply it to this diff. Suggestions only — never auto-applied; the user decides, because the project's naming and framework rules take precedence over "shortest".

## Output

Group findings:
- 🔴 **Critical**: violates spec / rules, or a bug. Must fix.
- 🟡 **Suggestion**: worth improving.
- 🟢 **Optional**.
- ✂️ **Over-engineering** (from section 3).

Each finding: `file:line — what — fix`. If nothing: say "符合 spec 与规范" and stop.

## 4. Lessons (only when there is a signal; skip for small tasks)

Ask nothing unless one of these is true:
- The result deviated from the spec → write a few lines to `docs/specs/<feature>/复盘.md`: what deviated, why.
- The same class of mistake appeared twice, or the review found a convention the rules do not cover → propose a short rule draft and ask whether to adopt it via the project's rule process. Never write rules without confirmation.

No signal → write nothing.
````
