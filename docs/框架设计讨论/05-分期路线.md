# 分期实现路线（草案）

未达成共识前仅为讨论骨架。分期边界会随讨论调整。

## 原则

- 先核心，再能力，再业务域
- 每一期结束应有可演示的「绑定轨迹」或可跑通的垂直切片
- 能延后的 SDK / 引导 / 热更等不阻塞核心验证

## 期次草案

### 第 0 期：设计冻结

- 完成讨论，锁定核心模型与分期范围
- 文档定稿：目标、核心接口草图、目录约定

### 第 1 期：核心底层

- 可绑定基类 + 绑定器
- 生命周期约定与错误边界
- 与 Bundle 的最小桥接（选定一种：绑定加载 / 解绑释放）
- 绑定可观测（列表 + 日志钩子）
- 最小示例：1 个示范模块可绑定/解绑

### 第 2 期：骨架能力

优先支撑「逻辑清晰 + 可跟踪」的底座（候选，待排序）：

- 日志 / 事件
- 资源（含 Bundle 管理器雏形）
- 任务（异步任务 / 流水线）
- 数据（本地存储 + 监听雏形）

### 第 3 期：视图 / 模块系统

- 场景 / 层级 / 弹窗 / 加载页
- 界面生命周期与显示层级
- 与可绑定模型对齐（避免双生命周期）

### 第 4 期：网络与实时

- HTTP / WebSocket
- 协议编解码扩展点
- 与流程/任务模块协作

### 第 5 期：体验向能力

- 音频、多语言、适配
- 定时器、对象池、触屏等管理器补齐

### 第 6 期：业务域模板

- 关卡基类
- 系统模块模板（邮件/商城等选 1 个打样）
- 交互：押注前中后消息插入流水线

### 第 7 期：平台与运营向

- SDK 抽象（登录/支付/广告/数数…）
- 热更 / 下载
- 新手引导

## 待讨论

- 第 1 期是否必须打通 Bundle，还是先纯逻辑可绑定、Bundle 放第 2 期？
- 业务域（系统/关卡）最早哪一期介入，以免抽象空转？
