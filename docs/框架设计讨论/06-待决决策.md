## 详细记录

### D01 — 框架交付形态与仓库边界

**问题：** 本仓库最终是「可复用的框架包」，还是「带框架的游戏工程模板」？

**推荐：** 混合——`packages/fframe-*` 做框架，根目录或 `examples/` 做示范游戏；一期可先单仓 monorepo，对外发包往后放。

**裁定：** **选 3（混合）。**

**影响：** 目录结构、是否发 npm/私有包、示例工程位置、分期验收标准。

---

### D02 — 可绑定对象与 Cocos 组件的关系

**问题：** 核心「可绑定基类」如何与 Cocos `Component` 共存？

**推荐：** 纯逻辑可绑定为主，UI 用薄桥接；或双轨。

**裁定：** **双轨。**  
- 涉及 UI：扩展 `Component` 做集成  
- 内部逻辑（如 data / control 等）：不强制集成 `Component`  
- 本窗口不展开 UI/业务细节；稍后有其他工程作参考时再综合

**影响：** 需要「统一生命周期约定」，但实现基类至少两条线（逻辑 / UI）。

---

### D03 — 统一契约形态

**问题：** 双轨之下，核心如何保证「同一套绑定/解绑生命周期」？

**推荐：** 共享接口 + 双基类；公共默认行为用小工具函数复用。

**裁定：** **选 1。** 通用部分做成共享接口；逻辑基类与 UI 组件基类各自实现；绑定器只认接口。

**影响：** 核心包导出物、绑定器能否无差别调度 UI 与逻辑对象。

---

### D04 — 核心常驻边界

**问题：** 核心底层「全项目必带」应包含哪些能力？其余一律 Bundle 绑定进入？

**推荐：** 驱动核心（极瘦 + 事件/任务/资源门面/日志）。

**裁定：** **选 2，并明确首批常驻：**
- 启动入口 / 驱动能力
- 可绑定共享接口 + 逻辑/UI 双基类（**公共部分也放核心**）
- 绑定器、Bundle 桥接
- **全局事件**
- **底层资源加载**
- **日志**
- 以后可以扩张核心名单；非驱动级能力（网络、音频、完整 UI、业务等）仍以 Bundle 绑定进入

**影响：** 包体积、启动路径、一期实现范围、与 Bundle 策略的衔接。

---

### D05 — 生命周期分两边

**问题：** 可绑定接口上，首版最少要约定哪些生命周期阶段？

**推荐：** 被调用者五阶段；启用/停用后扩。

**裁定：**
1. **调用者**：除调用绑定/解绑 Bundle 外，还负责是否存在、如何下载、下载成功后如何处理等编排
2. **被调用者**：在调用者流程各步上的回调；语义上为 **5 阶段**；为兼容其他场景，接口可做成 **7 阶段**（含启用/停用）

**影响：** 核心需同时定义「调用者编排 API」与「被调用者回调接口」；双基类落在被调用者侧。

---

### D06 — 调用者编排最小步骤

**问题：** 调用者侧绑定一条 Bundle/可绑定对象时，首版最少要固定哪些编排步骤？

**推荐：** 完整进场编排。

**裁定：** **选 2（完整进场），附加约束：**
- 进场：`解析目标` → `若未就绪则下载/拉取` → `下载成功后处理` → `创建被调用者（若需）` → `绑定` → `等到就绪` → `（可选）启用`
- 退场：`（可选）停用` → `解绑` → `销毁` → `（策略决定是否释放 Bundle/缓存）`
- **下载等步骤由上层逻辑决定是否触发，核心底层不自动触发**
- 核心提供编排能力与钩子位点，不替业务做「要不要下」的决策

**影响：** Bundle 桥接、下载与资源门面的职责切分、排障轨迹。

---

### D07 — 可绑定能力与 Bundle 的对应策略

**问题：** 「被绑定进来的功能」与 Cocos Bundle 如何对应？

**推荐：** 初荐一对多，后因文件夹管理与映射表成本修正为一对一。

**裁定：** **一对一。**
- 约定：功能目录 = Bundle = 一个可绑定单元；调用者按名字/路径解析，**不维护映射表**
- 纯逻辑、暂无资源：仍使用独立 Bundle（可为空资源包），不另开通道
- 一功能多包：后期扩张，不进核心首版

**影响：** 调用者解析目标、资源释放策略、工程目录规范。

---

**影响：** 启动入口形态、示范工程模板写法。
