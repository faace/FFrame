## 详细记录

### D01 — 框架交付形态与仓库边界

**问题：** 本仓库最终是「可复用的框架包」，还是「带框架的游戏工程模板」？

**推荐：** 混合——`packages/fframe-*` 做框架，根目录或 `examples/` 做示范游戏；一期可先单仓 monorepo，对外发包往后放。

**裁定：** **选 3（混合）。**

**影响：** 目录结构、是否发 npm/私有包、示例工程位置、分期验收标准。

---

### D02 — 可绑定对象与 Cocos 组件的关系

**问题：** 核心「可绑定基类」如何与 Cocos `Component` 共存？

**推荐：** 纯逻辑可绑定为主，UI 用薄桥接；或双轨。

**裁定：** **双轨。**  
- 涉及 UI：扩展 `Component` 做集成  
- 内部逻辑（如 data / control 等）：不强制集成 `Component`  
- 本窗口不展开 UI/业务细节；稍后有其他工程作参考时再综合

**影响：** 需要「统一生命周期约定」，但实现基类至少两条线（逻辑 / UI）。

---

### D03 — 统一契约形态

**问题：** 双轨之下，核心如何保证「同一套绑定/解绑生命周期」？

**推荐：** 共享接口 + 双基类；公共默认行为用小工具函数复用。

**裁定：** **选 1。** 通用部分做成共享接口；逻辑基类与 UI 组件基类各自实现；绑定器只认接口。

**影响：** 核心包导出物、绑定器能否无差别调度 UI 与逻辑对象。

---

### D04 — 核心常驻边界

**问题：** 核心底层「全项目必带」应包含哪些能力？其余一律 Bundle 绑定进入？

**推荐：** 驱动核心（极瘦 + 事件/任务/资源门面/日志）。

**裁定：** **选 2，并明确首批常驻：**
- 启动入口 / 驱动能力
- 可绑定共享接口 + 逻辑/UI 双基类（**公共部分也放核心**）
- 绑定器、Bundle 桥接
- **全局事件**
- **底层资源加载**
- **日志**
- 以后可以扩张核心名单；非驱动级能力（网络、音频、完整 UI、业务等）仍以 Bundle 绑定进入

**影响：** 包体积、启动路径、一期实现范围、与 Bundle 策略的衔接。

---

### D05 — 生命周期分两边

**问题：** 可绑定接口上，首版最少要约定哪些生命周期阶段？

**推荐：** 被调用者五阶段；启用/停用后扩。

**裁定：**
1. **调用者**：除调用绑定/解绑 Bundle 外，还负责是否存在、如何下载、下载成功后如何处理等编排
2. **被调用者**：在调用者流程各步上的回调；语义上为 **5 阶段**；为兼容其他场景，接口可做成 **7 阶段**（含启用/停用）

**影响：** 核心需同时定义「调用者编排 API」与「被调用者回调接口」；双基类落在被调用者侧。

---

### D06 — 调用者编排最小步骤

**问题：** 调用者侧绑定一条 Bundle/可绑定对象时，首版最少要固定哪些编排步骤？

**推荐：** 完整进场编排。

**裁定：** **选 2（完整进场），附加约束：**
- 进场：`解析目标` → `若未就绪则下载/拉取` → `下载成功后处理` → `创建被调用者（若需）` → `绑定` → `等到就绪` → `（可选）启用`
- 退场：`（可选）停用` → `解绑` → `销毁` → `（策略决定是否释放 Bundle/缓存）`
- **下载等步骤由上层逻辑决定是否触发，核心底层不自动触发**
- 核心提供编排能力与钩子位点，不替业务做「要不要下」的决策

**影响：** Bundle 桥接、下载与资源门面的职责切分、排障轨迹。

---

### D07 — 可绑定能力与 Bundle 的对应策略

**问题：** 「被绑定进来的功能」与 Cocos Bundle 如何对应？

**推荐：** 初荐一对多，后因文件夹管理与映射表成本修正为一对一。

**裁定：** **一对一。**
- 约定：功能目录 = Bundle = 一个可绑定单元；调用者按名字/路径解析，**不维护映射表**
- 纯逻辑、暂无资源：仍使用独立 Bundle（可为空资源包），不另开通道
- 一功能多包：后期扩张，不进核心首版

**影响：** 调用者解析目标、资源释放策略、工程目录规范。

---

### D08 — 核心如何「驱动」外围

**问题：** 游戏启动后，核心如何拉起并调度外围 Bundle 功能？

**推荐：** 入口脚本驱动。

**裁定：** **选 2。** 核心提供应用入口/启动器与绑定编排 API；具体「何时绑哪个」写在项目入口逻辑；核心不内置业务清单。清单若需要，属项目侧约定。

**影响：** 启动入口形态、示范工程模板写法。

---

### D09 — 编排失败时的错误与回滚策略

**问题：** 下载失败、绑定回调抛错、就绪超时等，核心默认怎么处理？

**裁定：** **失败尽量回滚**（历史会话已确认）：对称退场；默认释放本次 Bundle；不内置自动重试。

---

### D18 — assets 目录如何划分

**问题：** 如何兼顾「按功能自包含」与「和核心区分」？

**裁定：**
```text
assets/
  fframe/              # 核心
  main/                # 默认入口 main.scene + 一次性点火代码
  bundles/             # 功能父目录（与核心区分）
    <功能名>/          # 一功能一目录 = 一 Bundle（代码/资源/场景等自用）
```
- 功能不直接摊在 `assets/` 根下，统一进 `bundles/`
- 父目录名暂定 `bundles/`；若要改名可另议

---

### D19 — main 场景销毁后逻辑如何存活

**问题：** `main.scene` 会销毁并跳转，如何避免挂在其上的逻辑被一起删掉？

**推荐：** 2 为主，3 为补充。

**裁定：**
- **主路径（2）**：`fframe` 核心与启动编排为普通 TS 模块/单例，不依赖 `main` 节点存活
- `main` 上仅挂一次性 `Bootstrap`：点火 → 调入口逻辑 → 切场景；随后随场景销毁无关紧要
- **补充（3）**：确有跨场景 UI 根时再用 `addPersistRootNode`，不作为默认套路

### D20 — main.scene 是否迁入 assets/main/

**问题：** 默认启动场景文件放哪？

**推荐：** 迁入 `assets/main/main.scene`。

**裁定：** **选 1。** 场景与 Bootstrap 同目录；项目设置启动场景改指 `main/main`；保留 `main` 命名。

---

### D21 — 第1期目录 + 示范 Bundle 是否冻结

**问题：** 开机先加载谁？要不要现在定示范 Bundle？

**裁定：** **选 2（推荐）。**
- **正式开机序（登录/热更/大厅…）后置**：属项目入口策略，不进核心
- **加载方式**：已有调用者编排（逻辑触发 load → bind → 就绪），不另开套路
- **第 1 期要测**：分组 `bundles/Demo/`（标识为测试用），其下 2 个功能 Bundle：
  - `bundles/Demo/DemoHome`：可含场景；由 `main` 入口 load/bind
  - `bundles/Demo/DemoChild`：嵌套绑定用（home 内 `绑定子`）
- `Demo/` 仅为分组目录，不配成 Bundle；绑定名仍为叶子名 `DemoHome` / `DemoChild`
- `main` 入口职责草图：启核心 → load/bind `DemoHome`（其内再绑 child）→ 再切到 demo 场景
- 目录分支（D18–D20）一并冻结

---

### D22 — Bundle/功能命名风格

**问题：** 模块名用大驼峰还是小驼峰？是否允许 `-`？

**裁定：** **大驼峰（PascalCase）**；禁止连字符。变量/方法仍小驼峰。  
规则文件：`.cursor/rules/naming-bundles.mdc`

---

### D23 — bundles 下是否允许多层分组

**问题：** 能否 `bundles/Core/DemoHome` 这种分层？

**裁定：** **选 1。**
- 允许中间层分组目录（如 `Core/`），**不**配置为 Asset Bundle
- 仅**叶子功能目录**配置为一对一 Bundle
- 绑定名 / `loadBundle` 名 = **叶子目录大驼峰名**（如 `DemoHome`），不用全路径
- 首版不做 Bundle 套 Bundle

---

### D24 — 脚手架目录大小写

**问题：** `bundles`/`fframe`/`main` 与功能大驼峰混用是否改？

**裁定：** **选 1。** 小写 = 系统/脚手架位（对齐 Cocos `resources`）；大驼峰 = 功能与分组。已写入 naming rule。
